01 — WHAT THE AUDIT FOUND


The admin surface is broad but not operational
There are more than forty admin routes covering intake, positions, candidates, scoring, clients, payments,
operations, integrations and support. The coverage is genuinely good. The problem is that the surface is organised
by entity rather than by work: to find out what is going wrong today, a recruiter has to visit six screens and hold the
answer in their head.

— No single work queue. Attention-worthy jobs, stalled candidates, breached commitments and failed processing
  jobs each live on their own page, with no shared notion of priority or ownership.
— Aging is not computed anywhere the operator can see it. Stage history exists, but time-in-stage — the single
  most useful recruiting signal — is not surfaced on the pipeline.
— Ownership is implicit. Positions can be open, published and unowned. Nothing reassigns work when staff
  change.
— Exceptions fail quietly. Processing jobs, notification deliveries and integration syncs can all fail without any visible
  counter in the shell.
— Client readiness is manual. Before an update call, the admin reconstructs what changed by hand, from several
  screens.
— Error states still read as empty states in places. A failed query that renders 'no results' is worse than a crash,
  because the operator acts on it.
— Decision provenance is scattered. Approvals, overrides, rejections and stage moves are recorded in different
  tables with no unified timeline per candidate.


Six strengths worth protecting
— A canonical schema with real audit tables (audit_events, candidate_stage_history, score_decisions,
  evidence_overrides).
— Role-aware RLS with SECURITY DEFINER helpers, so permissions can be displayed by calling the same functions
  that enforce them.
— Immutable score runs and rubric versions — evaluation history is defensible to a client.
— Existing attribution and timing views (v_source_attribution, v_time_to_hire, v_portfolio_rollup) that most of these
  prompts simply need to surface.
— A working processing worker with claim logic and retries; exceptions need visibility, not a rewrite.
— Test-record flagging already in place, so operational counts can be kept clean.


Rules applied to every prompt in this pack
— Every number must be derivable from existing tables. No invented metrics, no imported benchmarks.
— Any rate shown must state its denominator, and be suppressed below a stated sample floor.
— Loading, empty and error are three distinct states. A failed query never renders as zero or empty.
— Every state-changing action writes an attributable audit row with an actor and, where it affects a client, a reason.
— Nothing becomes client-visible without a recorded approval.
— No decorative widgets, no fabricated activity, no gamification, no AI-authored client communication.

    01 Portfolio rollup with account health bands                                                 NOW · M

    PROBLEM            Admins open the dashboard and see totals, not which client accounts are actually in trouble.
                       Health is judged by memory and by whoever shouts loudest.
    SCREEN             /admin (index) — replace the top summary strip with a Portfolio Health table.
    DATA SHOWN         Per organization from v_portfolio_rollup and admin_clients_view: org name, plan/subscription
                       state, open positions, positions with zero submitted candidates, oldest open position age
                       (days), submissions in last 7 days, client decisions pending, days since last client-visible activity.
                       Exclude is_test_record orgs unless the existing test toggle is on.
    ACTIONS            Sort by any column; click a row to open /admin/clients/$id; toggle 'Show test records'.
    TRIGGER / LOGIC    Health band computed at query time: At risk = any open position with 0 submissions and age >
                       14 days, OR pending client decisions > 5, OR no client-visible activity in 10+ days. Watch = half
                       those thresholds. Healthy = neither.
    STATES             Loading: 6 skeleton rows. Empty: 'No active client accounts yet' + link to /admin/clients/new.
                       Error: inline error card with the failure reason and a Retry button — never an empty table.
    ACCEPTANCE         Every non-test org with at least one open position appears exactly once; band matches the
                       stated rule; row click lands on the correct client; error state renders on a forced query failure.
    DO NOT BUILD       No health 'score' out of 100, no trend sparkline, no colour-only signalling without a text label.
