BLOCKER F1 — Filtering by role tells the client “Nothing needs you today” while candidates wait on them /client?org=815fcb92…&preview=client_admin&role=bf2a3410-5d91-4b9f-b2e6-4816c724a3ad Steps Open the OMNIFLOW client overview. Saw (verbatim) Showing Technical Product Developer – Full Stack & Integrations only. Everything on this page — including the decision queue and the headline above — counts this role alone. Nothing needs you today 2 items checked. 12 applications are in review with TaaSFlow right now. 1 open role 2 waiting on your decision 0 roles with no shortlist yet Expected The same two candidates the unfiltered page lists. Instead the queue empties, while the tile beside it still reads 2 waiting on your decision — the page contradicts itself in a single viewport, and the empty half is the half that reads as good news. Code src/lib/client-overview.functions.ts — queue items are built from loadClientOpenItems , and OpenItem ( src/lib/client/open-items.server.ts ) carries no position_id field at all. The overview therefore invents one by parsing the link: position_id: item.href.split('/').pop()?.split('#')[0] || null, For a pending decision the href is /client/candidates/${row.id} , so position_id is a candidate match id. For an offer the href is /client/offers , so it is the literal string "offers" . For an interview it is "interviews?interview=…" . Only info_request items, whose href is /client/positions/${id}#information-needed , yield a real position id. The subsequent queue.filter(q => q.position_id === selectedRole) can therefore never match a decision, an offer or an interview. Shape A guard compared against a value the vocabulary does not contain (#2), producing failure rendered as emptiness (#4). The position id is available server-side — open-items.server.ts already uses row.position_id for the role caption — it is simply never carried onto the item. Why blocker The source comment directly above the filter predicts this exact harm: “a client could return to a bookmarked link and read ‘nothing needs you’ while three other roles waited.” The chip was added to mitigate it. The underlying filter is broken, so it happens even when the client selects the correct role. UX FIX Never let a filter empty a to-do list silently. If a filter removes every item, say “No open items for this role — 2 items on other roles are hidden by this filter,” with a one-click clear. And the tile row must obey the same filter as the queue, or it must not sit beside it. LOVABLE PROMPT Add a real position_id field to the OpenItem type in src/lib/client/open-items.server.ts and populate it from the row that creates each item (row.position_id for pending_decision and offer, interview.position_id for feedback, pending.position_id for interview, request.position_id for info_request). Then in src/lib/client-overview.functions.ts delete the line `position_id: item.href.split('/').pop()?.split('#')[0] || null` and use item.position_id directly. Today the role filter drops every pending decision because that expression returns a candidate match id, and the OMNIFLOW overview renders "Nothing needs you today" beside a tile reading "2 waiting on your decision". Add a unit test asserting that filtering by a role returns the decisions belonging to it. MINOR F9 — Processing states have no pinned domain, so the label map has drifted src/lib/vocabulary.ts Problem PROCESSING_STATUS_VOCABULARY knows queued, processing, completed, failed, skipped . The states actually stored and queried include parsing, parsed, enriching, ready_to_score, scoring, scored, manual_review_required, ocr_required — only queued overlaps. Unknown values fall through statusLabel() to sentenceCase() , which is why screens read ocr required and manual review required rather than designed copy. Root cause The same file solves this for positions, pinning the domain in POSITION_STATUS_VALUES against the migrations. There is no processing-state equivalent. F5 is the direct consequence.
